# Temperature_Sensor

ESP32-based temperature acquisition for RTDs (MAX31865 / PT100) and K-type
thermocouples (MAX31856), with Python tools on the PC side for **live plotting**
and **CSV logging** over USB serial.

The firmware streams temperatures as simple comma-separated lines; the Python
tools parse those lines, plot them in real time, and save them to disk. The
star of the PC side is [`temp_gui.py`](temp_gui.py) — a Tkinter GUI that works
with **any number of sensors**, plots them the moment you connect, and lets you
name the channels and choose a save folder while data is already streaming.

├── temp_logger_4.py        CLI logger hard-coded for RTD + 3 thermocouples
├── temp_logger.py          CLI logger for a single sensor

Logged CSVs (`temp_data.csv` and anything written to a chosen save folder) stay
on your machine — they are regenerated by running the logger and are not tracked.

> **Note on `src/`.** PlatformIO compiles every `.cpp` file in `src/`, so only
> `main.cpp` is actually built. The other files in `src/` (and everything in
> `test/`) are **reference sketches kept without a `.cpp` extension** so they do
> not all get compiled into one binary. To flash one of them, copy its contents
> into `main.cpp` (or give it a `.cpp` name and remove the others). `main.cpp`
> is currently a 2.4 GHz WiFi channel scanner, not a temperature sketch.

## Hardware

- **ESP32 dev board** (`board = esp32dev`).
- **MAX31865** RTD-to-digital converter for a PT100 (RTD).
- **MAX31856** thermocouple-to-digital converter(s) for K-type thermocouples.

Sensors share the VSPI bus; each has its own chip-select (CS) line. Typical
pinout used in `FullOven4Sensors`:

| Signal | ESP32 pin |
|--------|-----------|
| SCK    | 18        |
| MOSI   | 23        |
| MISO   | 19        |
| CS RTD (MAX31865) | 15 |
| CS TC1 (MAX31856) | 5  |
| CS TC2 (MAX31856) | 4  |
| CS TC3 (MAX31856) | 2  |

The PT100 wiring mode (`MAX31865_2WIRE / _3WIRE / _4WIRE`) must match your probe.

## Serial protocol

All PC-side tools speak the same line-oriented protocol at **115200 baud**:

| Line                       | Meaning |
|----------------------------|---------|
| `T,RTD,TC1,TC2,TC3`        | **Header** — column names. Fields are non-numeric. Sent once at startup (optional). |
| `T,23.45,150.22,148.9,nan` | **Data** — one reading per sensor, in header order. `nan` = sensor fault/missing. |
| `FAULT_RTD,0x80` (etc.)    | A fault report; shown to the user but not plotted. |

Rules the tools rely on:
- Every payload line starts with `T,`.
- A `T,` line whose fields are **non-numeric** is treated as the header (names).
- A `T,` line whose fields are **numeric** (or `nan`) is treated as a data row.
- The **number of sensors** is whatever count the data rows contain, so the same
  tools work for 1 sensor or 20.

## PC-side quickstart

### 1. Install Python dependencies

```bash
pip install -r requirements.txt
```

(`pyserial` and `matplotlib`; `tkinter` ships with the standard CPython
installer on Windows.)

> Close the PlatformIO serial monitor before running any tool — two programs
> cannot hold the same COM port at once.

### 2. Run the GUI (recommended)

```bash
python temp_gui.py
```

Workflow:
1. Pick your **COM port** and click **Connect**.
2. Plots appear automatically — one per detected sensor — with default names.
3. **Rename** each sensor in the panel on the left and click *Apply names*.
4. Click **Choose folder…**, set a file name, and hit *Start saving* to begin
   writing CSV. Any data captured before you started saving is written too, so
   nothing between connect and save is lost.

Viewing controls below the plot: **Show** picks how much time is visible
(*All* = everything since connect) and the **End of view** slider scrubs where
the view ends (far right = LIVE, following incoming data) — so you can view
start→now, start→any earlier point, or just the last few minutes. The control
panel is resizable via the sash between it and the plot, and can be hidden
with the *Hide panel* button. See [`temp_gui.py`](temp_gui.py) for other
options (separate vs. overlaid plots, etc.).

### 3. Or use a CLI logger

`temp_logger_arb.py` (arbitrary sensor count), `temp_logger_4.py`
(RTD + 3 TCs), and `temp_logger.py` (single sensor) are terminal-based
equivalents that prompt for the port, sensor names, and CSV path before
plotting. They remain for scripted/headless use.

## CSV format

Every logger — GUI and CLI — writes the same two time columns, following the
**lab timestamp convention** shared with the Rigol scope, Rb experiment runner,
ion-gauge pressure monitor and Alicat flow monitor:

```
# temperature log
# session_start: 2026-07-24 09:28:50.048
# timezone: Central Daylight Time (UTC-05:00)
# timestamp = local wall clock when the sample arrived, elapsed_s = seconds since session_start
timestamp,elapsed_s,RTD_C,TC1_C,TC2_C
2026-07-24 09:28:50.212,0.165,20.00,100.00,
```

| column | format | meaning |
| --- | --- | --- |
| `timestamp` | `YYYY-MM-DD HH:MM:SS.mmm`, local | wall clock when the sample arrived |
| `elapsed_s` | `%.3f` | seconds since the `session_start` in the header |

Both come off the same wall clock, so `timestamp − session_start` reproduces
`elapsed_s` exactly — that is what makes it valid to line a temperature trace up
against a pressure or flow log on `timestamp` alone. In the GUI, `session_start`
is the **connect** time, not when saving began, so back-filled rows carry their
own real acquisition times.

Load with `pd.read_csv(path, comment="#")`; a plain `csv.reader` needs the `#`
lines filtered out first. An empty cell is a sensor that reported `nan` for that
sample.

This replaced a single `time` column holding a bare `HH:MM:SS`, which could not
survive midnight, carried no date to align a multi-day bake against, and had no
sub-second resolution to match a 1 Hz scope frame with. **CSVs written before
this change have the old column and need reading differently.**

## Firmware build (PlatformIO)

```bash
pio run                 # build
pio run --target upload # flash the ESP32
pio device monitor      # view raw serial output
```

Dependencies (`Adafruit_BusIO`, `Adafruit_MAX31865`, `Adafruit_MAX31856`,
`Adafruit IO Arduino`) are pinned in [`platformio.ini`](platformio.ini) and
fetched automatically on first build.
